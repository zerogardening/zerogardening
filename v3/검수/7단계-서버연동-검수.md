## 3. 🔴-1 — html 4개에 `<<script`. 스크립트 한 개씩 통째로 안 실린다

`index.html`·`주문.html`·`업체.html`·`소싱.html`의 **26행**이 전부 이렇다.

```html
<<script src="https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2"></script>
script src="js/lib/xlsx.min.js"></script>      ← 앞의 '<' 를 CDN 줄이 먹었다
```

CDN 줄을 끼워 넣을 때 **바로 아래 줄의 여는 `<` 를 가져가 버렸다.**
HTML 파서는 `<<` 를 「`<` 라는 글자 + 새 태그」로 읽으므로, **다음 줄은 태그가 아니라 그냥 글자**가 된다.

**실제 브라우저(Chrome)로 확인했다.** 같은 모양의 최소 시험 페이지를 만들어 서버 접근 로그를 봤다.

```
GET /parse시험/a.html
GET /parse시험/두번째.js?t=1      ← 첫번째.js 는 요청조차 없다
```

| 파일 | 사라진 스크립트 | 그래서 |
|---|---|---|
| `주문.html` | **`js/lib/xlsx.min.js`** | 🔴 **`XLSX is not defined`.** 주문 엑셀 올리기·송장 파일 내보내기·배송완료 변환이 **전부 죽는다.** 우람님이 매일 쓰시는 기능이다 |
| `index.html` | `js/00-시드.js` | `ZG.시드`가 없다 → 새 기기·`?reset=1`·로그아웃 상태에서 `부팅()`이 `ZG.시드.심기()`에서 TypeError |
| `업체.html` | `js/00-시드.js` | 위와 같다 |
| `소싱.html` | `js/00-시드.js` | 위와 같다 |

덤으로 **`<body>` 맨 앞에 `<` 글자 하나가 그대로 찍힌다**(네 화면 전부).

이전 커밋 `94d3055`에는 네 파일 모두 `<script src="js/00-시드.js?v=12"></script>`(주문은 `xlsx.min.js`)가 멀쩡히 있었다. **이번 커밋이 낸 회귀다.**
`이사.html`(64행)만 정상이다.

**고칠 것** — 네 파일 26~27행. `<<script` 의 `<` 하나를 지우고 다음 줄 맨 앞에 `<` 를 되돌린다.

## 4. 🔴-2 — 캐시가 다른 탭 갱신을 못 본다. 탭 두 개면 입력이 사라진다

`01-저장소.js`의 캐시(35행 `var 캐시 = {}`)를 **무효화하는 곳이 어디에도 없다.**
`저장()`·`전부지우기()`가 자기 탭 캐시를 갱신할 뿐, 다른 탭이 localStorage를 바꿔도 이 탭은 옛 사본을 계속 돌려준다.

그런데 **`storage` 이벤트를 듣는 화면이 이미 4개 있다** — `07-앱.js:154`·`08b-주문목록.js:654`·`12-업체앱.js:156`·`14-소싱앱.js:149`.
넷 다 `다시그리기()`를 부르는데, 그 `다시그리기`가 `읽기()`로 **낡은 캐시**를 읽으므로 **화면이 안 바뀐다.** 있던 기능이 죽었다.

더 나쁜 것은 그다음이다. jsc로 재현했다.

```
탭 B가 한 번 읽는다 (캐시 채워짐)
탭 A가 입고 1건을 넣는다 → localStorage = [i1, i2, 탭A가 넣은 입고]
탭 B에서 입고를 하나 더 넣는다 (덧붙이기 → 낡은 캐시를 읽어 덮어쓴다)

localStorage 최종: ["i1","i2","탭B가 넣은 입고"]
FAIL 탭 A 입고가 사라졌다 — 데이터 유실
```

`01-저장소.js` 머리 주석이 **「다른 탭이 그 사이에 넣은 것을 지우지 않기 위해서다」**라고 약속한 바로 그 보장이 캐시 때문에 깨졌다.
설계 §4-1의 「동작은 100% 같다」도 이 대목에서 사실이 아니다.

- 로그인 + 온라인이면 Realtime이 몇 초 뒤 메워 준다(에코 맵은 탭마다 따로라 되돌아온 줄을 안 버린다)
- **밭에서 끊겼거나 CDN이 안 열리면 그대로 영구 유실이다.** 우람님은 상품 탭과 주문 탭을 같이 띄워 두신다

**고칠 것** — `01-저장소.js`에 한 줄이면 된다.

```js
window.addEventListener('storage', function (e) { if (e.key) delete 캐시[e.key]; });
```

(`전부지우기()`의 `캐시 = {}`는 그대로 둬도 된다.)

## B. 🔴-3 — 같은 줄을 동시에 고치면 두 기기가 **영원히 갈라진다** (§9-6 · §5 위반)

**증상** — A와 B가 0.2초 차로 같은 품목의 유통명을 저장. 20초를 기다려도 A는 `동시A`, B는 `동시B`. 서버는 `동시B`.
설계 §5 「진 쪽 화면도 Realtime으로 곧 이긴 값으로 바뀐다 — **조용히 어긋난 채 남지 않는다**」를 정면으로 어긴다.

**원인** — `01b-서버.js` 의 에코 무시가 **`표+id` 만으로 5초간** 막는다. 값을 안 본다.

```js
function 에코등록(표, id) { 에코[표 + '|' + id] = Date.now(); }   // 값이 없다
function 받은줄(표, p) { … if (에코중(표, 행.id)) return; … }      // 남이 보낸 것도 같이 버린다
```

내가 저장한 직후 5초 안에 **상대가 보낸 새 값**이 도착하면 그것도 「내 메아리」로 보고 버린다.
Realtime 은 그 줄을 다시 보내지 않으므로 **새로고침 전까지 복구되지 않는다.**

**대조 실험** — 같은 줄을 **8초 간격**(에코창 밖)으로 고치면 A·B 둘 다 `느린B` 로 맞는다. 원인 확정.

**고칠 방향(참고)** — 에코 열쇠에 **보낸 값의 해시(또는 `JSON.stringify` 사본)** 를 같이 담고, 되돌아온 `내용`이 그것과 **같을 때만** 버린다. 다르면 남의 값이므로 받아들인다.

> 실무 영향 — 우람님과 두용씨가 같은 주문을 거의 동시에 만지면 **서로 다른 값을 본 채 장사한다.** 이번 단계를 만든 첫째 이유(§5)가 그대로 깨진다.

## A. 🔴-5 — 같은 줄을 동시에 고치면 **두 화면이 값을 서로 바꿔 든다** (🔴-3 미해결)

### 실측 — 6회 시험, **일치 0/6**

같은 품목(`ACC01-10`)의 유통명을 A·B 가 **0.01초 간격**으로 저장하고 **20초** 기다렸다.

```
1회차 (A 먼저)  A=B1  B=A1  서버=B1   🔴
2회차 (B 먼저)  A=B2  B=A2  서버=A2   🔴
3회차 (A 먼저)  A=B3  B=A3  서버=B3   🔴
4회차 (B 먼저)  A=B4  B=A4  서버=B4   🔴
5회차 (A 먼저)  A=B5  B=A5  서버=A5   🔴
6회차 (B 먼저)  A=B6  B=A6  서버=A6   🔴
```

**A 는 언제나 B 의 값을, B 는 언제나 A 의 값을 든다.** 이긴 쪽(서버와 같은 값을 보낸 쪽)이 늘 **자기 화면에서만 진 값을 본다.**
새로고침 전까지 안 돌아온다. 설계 §5 「조용히 어긋난 채 남지 않는다」를 그대로 어긴다.

### 원인 — Realtime 도착/반영을 그대로 찍었다

두 브라우저에 감시 채널을 따로 붙여 **「도착한 값」과 「실제로 반영한 값」**을 나눠 기록했다.

```
A 기록: ["도착:추적A", "적용→추적B", "도착:추적B"]      ← 내 값(추적A) 버림 ✅ · 남의 값 받음 ✅
B 기록: ["도착:추적A", "적용→추적A", "도착:추적B"]      ← 남의 값 받음 ✅ · 그 다음 내 값(추적B) 버림 🔴
끝: A=추적B  B=추적A  서버=추적B
```

`01b-서버.js` 의 `에코중()` 은 **5초 안에 돌아온 내 값이면 무조건 버린다.**
그런데 B 는 그사이 **남의 값(추적A)을 이미 자기 위에 덮어썼다.** 그 시점에서 B 가 보낸 값은 이제 「메아리」가 아니라 **서버가 들고 있는 최신값**이다. 그걸 버리니 B 만 옛 값에 남는다.

🔴-3 수정은 **「내용까지 견준다」까지만** 갔고, **「내 로컬이 아직 그 값인가」**를 안 본다.

### 고칠 방향 (참고) — 에코 표를 아예 없애도 된다

되돌아온 값을 **지금 로컬에 있는 그 줄**과 견주면 두 경우가 한 줄로 풀린다.

```js
// 받은줄() 안, 목록/자리를 찾은 다음
var 같음 = 자리 >= 0 && 지문(목록[자리]) === 지문(행.내용);
if (같음 && !지움) return;        // 이미 같다 → 화면 안 건드린다 (에코든 남의 것이든 결과가 같다)
```
- 내 메아리 → 로컬이 이미 그 값 → 건너뛴다(화면 안 튄다). **지금 동작 그대로**
- 남이 덮은 뒤 온 내 값 → 로컬이 달라졌다 → **받는다.** 갈라짐이 사라진다

### 왜 — `수정시각` 이 **커밋 순서와 거꾸로** 찍힌다

| 회차 | 서버에 남은 값 | 그 값의 `수정시각` | 밀려난 값 | 그 값의 `수정시각` |

**세 번 다 「서버에 최종으로 남은 값」이 오히려 더 작은 `수정시각`을 갖는다.**
트리거가 `new.수정시각 := now()` 인데 **`now()` 는 트랜잭션이 시작한 시각**이다.
두 기기가 같은 줄을 건드리면 뒤에 온 트랜잭션은 **행 잠금 앞에서 기다렸다가 나중에 커밋**되는데,
그 줄에 찍히는 시각은 **기다리기 전 시각**이라 먼저 커밋된 쪽보다 작다.
즉 **경합이 일어난 바로 그 순간에만 `수정시각` 순서가 뒤집힌다** — 이 고침이 노린 상황이 정확히 그 자리다.

마이크로초 비교 자체는 잘 돈다(형식 `2026-08-06T09:55:36.581215+00:00` 확인, `Date.parse` 정상).
**틀린 건 비교가 아니라 견주는 대상이다.**

### 고칠 방향 (고치지 않았다)

`v3_손댐()` 트리거의 `now()` 를 **`clock_timestamp()`** 로 바꾼다. SQL 한 줄이다.
`clock_timestamp()` 는 **행 잠금을 얻고 UPDATE 를 실제로 실행하는 순간** 값을 낸다 —
나중에 쓴 쪽이 **반드시** 더 큰 시각을 갖는다. `01b-서버.js` 는 손댈 것이 없다.
