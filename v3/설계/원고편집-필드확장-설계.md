# AI 상품글쓰기 — 상품타입별 필드 확장 설계

> 🔴 **대상: `통합관리/app.html` (실서비스). v3 재개발이 아니다.**
> 이 문서는 v3 설계서들과 무관하다. 지금 돌아가는 파일을 직접 고치는 설계다.
> 작성 2026-09-23 · `dev-architect` · 근거는 app.html 실코드와 `상품/_템플릿/` 실파일뿐이다.

---

## 0. 무엇이 문제인가

`AI_FIELDS`(app.html:14600)는 **모든 상품이 같은 칸을 본다**는 전제로 짜였다.
상세페이지 칸은 넷 — `detail_intro` · `detail_flower` · `detail_leaf` · `detail_growing`.

그런데 구근은 **받는 순간 잎이 없다.** 그래서 지금 현장에서는 `detail_leaf`(잎)에
**심는 법**을 적어 넣고 있다. 실증 — `상품/품목/튤립-블루패럿(12+)/작성내용.md`:

```
### detail_leaf
> 🔴 구근은 잎 구역이 없다 — 심는 법을 넣는다.
```

칸 이름과 들어가는 내용이 어긋나 있다. 게다가 구근 5구역(「구근 크기」)에 대응하는 칸은 아예 없다.
**땜질로 튤립만 분기하면 목본·다육이 올 때 같은 일을 또 한다.** 칸 목록을 **템플릿별로 나눈다.**

### 범위

| | |
|---|---|
| 들어간다 | 포트묘 마스터 양식(`상세페이지-양식.html`) · 구근 **개별상품**(`구근-개별상품-시안/`) |
| 안 들어간다 | **구근 묶음**(`구근-상세페이지-시안/`) — 한 페이지에 품종 카드 여러 장이라 **SKU 한 건의 원고가 아니다.** 카드가 쓰는 값은 꽃설명 + 식물 특성이라 단품 필드를 그대로 재사용하면 된다. 새 템플릿 키를 만들지 않는다 |
| 안 건드린다 | 카페24 칸 9개 · `note` · 폴더 큐(AIBridge) 구조 · 화면 디자인 |

## 1. 새 DB 컬럼이 필요한가 — **아니다**

저장소를 확인했다. app.html의 모든 상태는 **Supabase `app_meta` 테이블의 `key='state'` 한 행, `value` JSON 한 덩어리**다
(app.html:4404·4413·4425). SKU 마스터는 그 안의 `state.skus[]` 배열이다.

→ **SKU 레코드에 키를 하나 더 얹는 데 DDL이 필요 없다.** 새 표도 만들지 않는다.
(v3에서 이 JSON 한 덩어리 구조를 표로 쪼갤 예정이지만, **그건 v3 일이다.** 여기서는 손대지 않는다.)

### 지금 레코드에 「템플릿 종류」 값이 있는가 — 없다

백업(`제로가드닝_백업_2026-08-02.json`) 기준 `skus[]`의 키는 19개다:
`barcode · distributionName · scientificName · heightMin/Max · widthMin/Max · hardiness · watering · sunlight · bloomStart/End · note · aiFields · aiUncertainTraits · aiUpdatedAt · id · createdAt · updatedAt`.
**분류·카테고리 성격의 값이 하나도 없다.**

🔴 **`fillTypeSelect`(app.html:16294)의 `관목·숙근·관엽·그라스·구근`은 SKU와 무관하다.**
그건 **소싱 모듈 전용**(경쟁사 진단·키워드)이고 SKU 레코드에 저장되지 않는다. **1:1로 쓸 수 없다.**

### → 새 키: `productTemplate` (SKU 마스터, 문자열)

| | |
|---|---|
| 위치 | `state.skus[].productTemplate` |
| 값 | `'master'` \| `'bulb'` (앞으로 늘어난다) |
| 없을 때 | **`'master'`로 본다** — 기존 145개 SKU는 화면이 1픽셀도 안 바뀐다 |
| 입력 | 🔴 **타이핑 금지. 기본정보 칸의 `<select>`** (품목코드 손입력 오류 11종이 실제로 났다) |
| 입고(receivings) | **내려보내지 않는다.** SKU 단위 값이다. `recvPatch`에 넣지 않는다 |

## 2. 새 데이터 구조

지금의 평면 배열 하나(`AI_FIELDS`)를 **셋으로 나눈다.**

```
AI_COMMON_FIELDS   카페24 9칸 — 템플릿과 무관하게 항상 나온다 (지금 것 그대로 이동)
AI_FIELD_LIB       상세페이지 칸 사전.  id → {label, maxChars, rows, guide, legacyFrom?}
AI_TEMPLATES       템플릿 레지스트리.   key · label · fields[] · infer()
```

`AI_TEMPLATES[].fields[]`의 원소는 **문자열(사전 id 그대로)** 또는 **`{id, label?, guide?, rows?, maxChars?}`(덮어쓰기)** 둘 다 받는다.
같은 칸을 템플릿마다 다른 말로 안내해야 하기 때문이다(구근 2구역 = 마스터 꽃 칸).

```
AI_PLATFORMS 는 그대로 둔다 (cafe24 / detailpage). 플랫폼 ≠ 템플릿이다.
detailpage 패널의 "내용물"만 템플릿에 따라 달라진다.
```

### 판별 함수 (새로 만든다, 3개)

| 시그니처 | 하는 일 |
|---|---|
| `inferAiTemplate(sku) → 'bulb' \| ''` | 저장값이 없을 때만 쓰는 **추천값**. 입고 규격(`spec`)에 `구근`, 품목코드 꼬리에 `BULB`(`SPEC_CODE_WORDS`, app.html:5332), 또는 유통명·학명이 `튤립\|수선화\|히아신스\|무스카리\|알리움\|크로커스\|상사화\|Tulipa\|Narcissus\|Hyacinthus\|Muscari\|Allium\|Crocus` 에 걸리면 `'bulb'` |
| `resolveAiTemplate(sku) → key` | `sku.productTemplate` → 없으면 `inferAiTemplate` → 없으면 `'master'`. **추론이 저장값을 덮지 않는다** |
| `aiFieldsFor(skuOrKey) → Field[]` | `AI_COMMON_FIELDS` + 해당 템플릿의 detailpage 칸(덮어쓰기 적용). **`AI_FIELDS`를 직접 쓰던 자리는 전부 이 함수를 부른다** |

🔴 `AI_FIELDS` 상수는 **지운다.** 남겨두면 두 벌이 되어 반드시 어긋난다.
`AI_FIELDS.length`를 쓰던 토스트 세 곳은 `aiFieldsFor(sku).length`로 바꾼다.

## 3. 템플릿별 필드 정의

### 3-1. 공통 — `AI_COMMON_FIELDS` (모든 템플릿)

지금 `platform:'cafe24'`인 9칸을 **한 글자도 고치지 않고** 옮긴다.
`cafe24_summary · brief · extra · searchTerms · browserTitle · metaAuthor · metaDesc · metaKeywords · imgAlt`

### 3-2. `AI_FIELD_LIB` — 상세페이지 칸 사전

| id | label | 최대 | rows | 설명(guide) 요지 | 비고 |
|---|---|---|---|---|---|
| `detail_intro` | 식물 전반 소개 (1-2줄) | 100 | 2 | 지금 그대로 | 두 템플릿 공용 |
| `detail_flower` | 꽃의 특징 (1줄) | 80 | 2 | 지금 그대로 | 두 템플릿 공용 |
| `detail_leaf` | 잎의 특징 (1줄) | 80 | 2 | 지금 그대로 | **마스터 전용** |
| `detail_growing` | 재배 가이드 (3가지) | 400 | 6 | 지금 그대로 | 두 템플릿 공용 |
| `bulb_planting` | **심는 법 (1줄)** | 120 | 3 | 「깊이·간격·뾰족한 쪽」 셋을 한 줄로. 양식 고정문구(언제 심나요·깊이와 방향 도해)와 겹치지 않게 **자리 고르는 기준**을 쓴다. 예: "구근 높이의 세 배 깊이에 뾰족한 쪽을 위로, 10~15cm 간격으로" | **신규** · `legacyFrom:'detail_leaf'` |
| `bulb_size` | **구근 크기 설명 (1줄)** | 80 | 2 | 규격 숫자가 **지름이 아니라 둘레**라는 걸 먼저 말한다. 둘레→지름 환산 + 동전 비교. 예: "12cm+ 는 둘레가 12cm 이상 — 지름 3.8cm쯤, 500원 동전보다 큽니다" | **신규** · 마스터엔 없던 칸(5구역) |

### 3-3. `AI_TEMPLATES` — 레지스트리

| key | label | 원본 양식 | 칸 구성 |
|---|---|---|---|
| `master` | 포트묘 (기본 양식) | `상품/_템플릿/상세페이지-양식.html` | `detail_intro` · `detail_flower` · `detail_leaf` · `detail_growing` — **지금과 완전히 같다** |
| `bulb` | 구근 개별상품 (시안) | `상품/_템플릿/구근-개별상품-시안/` | `detail_intro`(덮어쓰기) · `detail_flower`(덮어쓰기) · `bulb_planting` · `detail_growing`(덮어쓰기) · `bulb_size` |

**구근 6구역 ↔ 칸 대응**

| 구역 | 구근 단품 | 프로그램 칸 |
|---|---|---|
| 1 | 표지 — 품종명·학명·기본정보 6칸·소개 | `detail_intro` (덮어쓰기: **품종명으로 문장을 연다.** 품종명 검색 유입이 이 상품의 존재 이유다) |
| 2 | 심어서 보기까지 — 한 해 띠 + 미니스펙 | `detail_flower` (덮어쓰기 label `꽃의 특징 (2구역)`. **띠·미니스펙은 식물 특성 값에서 나오므로 글칸은 꽃 묘사 하나면 된다**) |
| 3 | **심는 법** — 흙 단면도 | **`bulb_planting`** ← 지금 `detail_leaf`에 들어가 있는 내용 |
| 4 | 재배 — 볕과 물·꽃진 뒤·이듬해 | `detail_growing` (덮어쓰기: 3항목을 **볕과 물 / 꽃이 진 뒤 / 이듬해에 또 보려면** 으로 고정) |
| 5 | **구근 크기** — 둘레→지름 | **`bulb_size`** ← 지금 칸이 없다 |
| 6 | 실제 발송 상품 | **칸 없음.** 규격에서 나오는 상용구다(마스터도 같다) |

🔴 **2구역에 `bulb_flower`를 새로 만들지 않았다.** 지금 구근 SKU의 `detail_flower`에 **이미 맞는 값이 들어 있다**
(작성내용.md 확인). id를 갈면 그 값이 고아가 된다. **이름표만 바꾸면 되는 것은 덮어쓰기로 끝낸다.**
바뀌는 건 `detail_leaf`(뜻이 어긋난 칸) 하나뿐이다.

## 4. 하위호환 — 마스터 4칸은 깨지지 않는다

🔴 **먼저 고쳐야 할 버그가 하나 있다.** app.html:11386 의 저장은

```js
aiFields: aiFieldsCollected,   // ← 화면에 그려진 textarea 만 모은 것
```

로 **통째 교체**다. 화면에 없는 키는 저장하는 순간 **사라진다.**
(백업에 `naver_*`·`coupang_*` 키가 남아 있는 건 그 SKU를 그 뒤로 저장한 적이 없어서일 뿐이다.)

템플릿별로 칸이 달라지면 이 버그가 곧바로 사고가 된다 — 구근 SKU를 저장하면 `detail_leaf`가 날아간다.

**→ 반드시 머지로 바꾼다.**

```js
aiFields: Object.assign({}, existingMaster.aiFields || {}, aiFieldsCollected)
```

이 한 줄이 이번 설계의 안전장치다. 이게 들어가면:

| 상황 | 결과 |
|---|---|
| 기존 SKU 145개 (`productTemplate` 없음) | `'master'`로 렌더 → **화면·필드 id·순서 모두 지금과 동일** |
| 구근 SKU를 `bulb`로 바꿔 저장 | `bulb_planting`·`bulb_size`가 **추가**된다. `detail_leaf` 값은 **그대로 남는다** |
| `bulb` → `master`로 되돌림 | `bulb_*` 값이 화면에서 빠질 뿐 **데이터는 남아 있다.** 다시 바꾸면 되돌아온다 |
| 이미 발행된 품목의 md 원고 | **영향 없다.** 프로그램은 md를 읽지도 쓰지도 않는다 |

### `legacyFrom` — 한 번만 도와준다

`bulb_planting`이 비어 있고 `detail_leaf`에 값이 있으면 **그 값을 초기 표시**하고
칸 옆에 `잎 칸에서 가져옴` 배지를 단다. 저장하면 `bulb_planting`에 들어가고 `detail_leaf`는 건드리지 않는다.
**일회성 마이그레이션 스크립트를 돌리지 않는다** — 구근 SKU가 12개 남짓이고, 자동 변환은 되돌리기 어렵다.

| 11331-11333 | 저장용 FormData 수집 | **그대로.** 이미 `select[name]`을 긁는다 |

### 새로 붙이는 이벤트 하나

기본정보의 `productTemplate` select가 바뀌면 **AI 패널을 즉시 다시 그린다.**
14744의 `change` 핸들러 안에 분기를 더한다 —
현재 DOM의 `textarea[name^="ai_"]` 값을 먼저 모아 `s.aiFields`에 덮어쓴 뒤 다시 렌더한다.
🔴 **안 그러면 양식을 바꾸는 순간 입력 중이던 글이 날아간다.**

`AIBridge` 큐 구조 · 폴더 권한 · 폴링 · `AI_NOTE_META` · 카페24 9칸 내용 · 화면 디자인 · Supabase 스키마.

## 6. 확장 시나리오 — 목본 전용 양식이 생긴다면

**손대는 곳은 두 군데뿐이다. 함수는 하나도 안 고친다.**

1. `AI_FIELD_LIB`에 새 칸을 적는다 (없으면 생략) — 예 `woody_pruning`, id는 **접두어로 갈라 둔다**
2. `AI_TEMPLATES`에 한 칸 더한다

```
{ key:'woody', label:'목본 (전용 양식)',
  fields:['detail_intro','detail_flower','detail_leaf','woody_pruning',
          {id:'detail_growing', guide:'...'}],
  infer: sku => /묘목|관목|나무/.test(...) ? 'woody' : '' }
```

3. **끝이다.** 기본정보 select 옵션은 `AI_TEMPLATES`에서 자동으로 늘고,
   `_renderAiFieldsHtml` · `_buildRequest` · `buildPromptText` · 저장 · 폴링은 **한 줄도 안 바뀐다.**
4. 기존 SKU는 전부 `master` 그대로 — **영향 없다.**
5. 외부 한 곳: Cowork 쪽 글쓰기 처리기(`.claude/skills/zg-ai-writing/SKILL.md` 자리)에 새 칸의 톤·예시를 적는다.

이 조건(2군데)이 이번 설계의 합격선이다. **함수를 고쳐야 새 양식이 붙는다면 설계가 틀린 것이다.**
