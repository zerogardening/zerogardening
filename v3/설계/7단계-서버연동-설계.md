# 7단계 — 서버 연동(실시간 양방향) 설계

**지시** — 「웹·앱이 실시간 연동. 어디서 수정하든 적용되게, 데이터도 실시간으로 올리면 서로 보이게.」
지금 v3는 localStorage 뿐이라 밭에서 폰으로 넣은 게 사무실 PC에 안 보이고 브라우저를 지우면 사라진다.

**바꾸지 않는 것** — 화면 40개 파일·CSS·시안은 한 글자도 안 건드린다. 관문은 `js/01-저장소.js` 한 파일이다.
공통 규약(CSS 변수·애니메이션·접근성·품목코드)은 **1단계 설계 그대로.**

## 0. 고른 방식과 이유

**메모리 캐시 + 줄 단위 서버 표 + Realtime 구독.** 구 `app.html` 방식을 뼈대로 쓰되 **한 덩어리 JSON을 줄 단위로 쪼갠다.**

| 왜 이 쪽인가 |
|---|
| `읽기()`는 **동기 그대로** 둔다 — 호출부 42곳을 async로 못 바꾼다 |
| 서버가 죽어도·인터넷이 끊겨도 **화면은 뜬다.** 캐시(=localStorage)를 먼저 그리고 서버는 도착하는 대로 덮는다 |
| 줄 단위라 폰과 PC가 **서로 다른 줄**을 동시에 고치면 둘 다 산다. 지금 방식은 하나가 죽는다 |
| 새 도구 없음 — Supabase JS(구 프로그램이 이미 쓰는 것) 한 개뿐 |

🔴 **`app_meta`의 `key='state'`는 읽지도 쓰지도 않는다.** v3는 `v3_` 로 시작하는 새 표만 쓴다.

## 1. Supabase 표 구조 — 대시보드 SQL Editor에 그대로 붙여 넣는다

표 15개 중 **배열 12개는 각각 한 표**(줄 하나 = 행 하나), **객체 3개 중 2개**(동봉카드설정·키워드)는 `v3_공유설정`에 한 행씩.
🔴 **`설정`은 서버에 안 올린다** — 마지막탭·스키마버전·시드완료·마지막입고업체는 **기기마다 달라야 하는 값**이다.

칸은 다섯이다 — `id`(원본 그대로. 품목만 `품목코드`) · `내용`(그 레코드 하나. jsonb) · `삭제됨` · `수정시각` · `수정자`.
칸을 전부 펼치지 않는 이유: v3는 서버에 질의하지 않고 **전량을 받아 브라우저에서 계산**한다. 칸을 늘리면 앱에서 필드 하나 더할 때마다 `ALTER TABLE`이 따라온다.

```sql
-- ① 표 12개 + 공유설정 1개 (한 번만 실행)
create or replace function public.v3_손댐() returns trigger language plpgsql as $t$
begin new.수정시각 := now(); new.수정자 := auth.uid(); return new; end $t$;

do $$
declare t text; n text;
begin
  foreach t in array array['품목','입고','출고','재고조정','업체','주문','주문묶음',
                           '명세서','명세서줄','견적요청','즐겨찾기','분류폴더','공유설정']
  loop
    n := 'v3_' || t;
    execute format('create table if not exists public.%I (
        id text primary key,
        내용 jsonb not null,
        삭제됨 boolean not null default false,
        수정시각 timestamptz not null default now(),
        수정자 uuid default auth.uid())', n);
    execute format('drop trigger if exists 손댐 on public.%I', n);
    execute format('create trigger 손댐 before update on public.%I
        for each row execute function public.v3_손댐()', n);
    execute format('create index if not exists %I on public.%I (수정시각)', n||'_시각', n);
    begin
      execute format('alter publication supabase_realtime add table public.%I', n);
    exception when duplicate_object then null;
    end;
  end loop;
end $$;
```

`v3_공유설정`에는 행이 셋뿐이다 — `id='동봉카드설정'` · `id='키워드'` · `id='서버상태'`(§4-3 관문 ①. SQL로 미리 넣지 않는다 — **없는 것이 「아직 안 올렸다」는 뜻이다**).

## 2. RLS — 로그인한 사람만, 익명은 전부 차단

지금 공개키로 `app_meta`를 받으면 `[]` 2바이트가 온다(실측). 새 표도 같은 규칙으로 간다.
**계정을 나눠 권한을 다르게 주지 않는다** — 우람님과 두용씨는 같은 데이터를 같이 본다.

```sql
-- ② RLS (①과 같은 창에서 이어서 실행)
do $$
declare t text; n text;
begin
  foreach t in array array['품목','입고','출고','재고조정','업체','주문','주문묶음',
                           '명세서','명세서줄','견적요청','즐겨찾기','분류폴더','공유설정']
  loop
    n := 'v3_' || t;
    execute format('alter table public.%I enable row level security', n);
    execute format('revoke all on public.%I from anon', n);
    execute format('drop policy if exists "로그인한사람만" on public.%I', n);
    execute format('create policy "로그인한사람만" on public.%I
        for all to authenticated using (true) with check (true)', n);
  end loop;
end $$;
```

## 3. 로그인 — v3에 로그인 화면을 새로 만들지 않는다

구 프로그램 `통합관리/index.html`이 이미 이메일·비밀번호 로그인과 `?from=` 되돌아가기(같은 origin만 허용)를 갖고 있다.
**GitHub Pages에서 v3와 origin이 같으므로 그대로 쓴다.** 계정도 우람님 것 그대로다.

- v3 페이지 5개(`v3/index.html`·`주문`·`업체`·`소싱`·`이사`)는 열릴 때 세션을 확인하고, 없으면 `../index.html?from=<지금주소>`로 보낸다
- 세션 확인은 **동기로** 한다 — supabase-js가 localStorage에 넣어 둔 `sb-vjqfhwrgrocapcyndgtx-auth-token` 존재 여부. 화면 그리기 전에 판단이 끝나야 하기 때문이다. 진짜 검증은 첫 요청이 401로 튕기는 것으로 하고, 튕기면 그때 로그인으로 보낸다
- 로그아웃 버튼은 **이번에 안 만든다**(화면 변경이라 `dev-designer` 몫). 필요하면 구 프로그램에서 로그아웃하면 세션이 같이 끊긴다

## 4. `01-저장소.js`를 어떻게 고치나 — 함수별

**새 파일 둘** (번호 체계는 지금 그대로 이어붙인다)

| 파일 | 하는 일 | 상한 |
|---|---|---|
| `js/01b-서버.js` | Supabase 클라이언트 · 로그인 게이트 · 첫 내려받기 · Realtime 구독 · 다시그리기 배분 | 250줄 |
| `js/01c-보내기.js` | 보낼것 큐(localStorage) · upsert 전송 · 재시도 · 온라인 감지 | 150줄 |
| `js/99b-서버올리기.js` | 이사 화면의 「☁ 서버로 올리기」 버튼 (§7) | 120줄 |

싣는 순서 — `supabase-js CDN` → `00-시드` → `01-저장소` → `01b-서버` → `01c-보내기` → 나머지. 5개 html 전부 `?v` 올린다.
CDN이 안 열리면(밭에서 끊김) `window.supabase`가 없다 → **조용히 로컬 전용으로 떨어진다. 화면은 그대로 뜬다.**

### 4-1. `01-저장소.js` 고치는 곳

🔴 **지금 `01-저장소.js` 114행은 `전체쓰기: 쓰기` 다 — 둘이 같은 함수다.** 그리고 `덧붙이기`·`바꾸기`·`지우기`가 전부 그 `쓰기`를 부른다.
대조 로직을 `쓰기` 안에 넣으면 **같은 줄이 큐에 두 번 실린다.** 그래서 **내부용과 외부용을 이름부터 나눈다.**

| 함수 | 어디 | 바뀌는 것 |
|---|---|---|
| **(신설) 캐시** | 내부 | 모듈 안 `var 캐시 = {}`. 키 → 값 |
| **(개명) `저장(k,값)`** | **내부 전용. 밖으로 안 내보낸다** | 지금의 `쓰기`가 이 이름이 된다. localStorage 저장 + 캐시 교체, **그게 전부다. 큐를 건드리지 않는다** |
| `읽기(k)` | 밖 | **시그니처·반환 모양 그대로 동기.** 캐시에 없으면 localStorage에서 읽어 캐시에 넣고, **캐시본의 깊은 복사**를 돌려준다. 지금은 매번 `JSON.parse`를 하고 있었으므로 **동작은 100% 같고 속도는 같거나 빠르다** |
| `덧붙이기(k,레코드)` | 밖 | 지금 그대로 + `저장()` + **`ZG.보내기.줄(k, 레코드)` 한 줄** |
| `바꾸기(k,id,변경)` | 밖 | 지금 그대로 + `저장()` + **`ZG.보내기.줄(k, 대상)` 한 줄** |
| `지우기(k,id)` | 밖 | 지금 그대로 + `저장()` + **`ZG.보내기.삭제(k, id)` 한 줄**. 서버는 행을 지우지 않고 `삭제됨=true`로 둔다(업무규칙 §8) |
| **(신설) `전체쓰기(k,배열)`** | 밖 | **`저장`을 가리키던 이름이 이제 새 함수를 가리킨다.** ①이전 캐시와 **줄 단위 대조**(`id`별 JSON 문자열 비교) → 새 줄·달라진 줄은 `ZG.보내기.줄`, 사라진 줄은 `ZG.보내기.삭제` ②그다음 `저장()`. 부르는 곳은 `10a-업체자료`·`13a-소싱자료`·`13c-검색량`·`09b-카드설정`·`00-시드`·`99-이사` |
| **(신설) `조용히(참거짓)`** | 밖 | 켜 두면 `전체쓰기`가 **큐를 건너뛰고 `저장`만 한다.** `00-시드.js 심기()`와 `99-이사.js 넣기()`를 **이 스위치로 앞뒤만 감싼다**(각 파일에 두 줄. 전체쓰기 호출 13곳은 안 건드린다) — 목데이터·이사분이 저절로 서버로 새어 나가지 않게 |
| `설정쓰기` | 밖 | **안 바꾼다.** 설정은 기기별이라 서버에 안 간다 |
| `동봉카드설정쓰기` | 밖 | + `ZG.보내기.설정('동봉카드설정', s)` |
| `전부지우기` | 밖 | 로컬·캐시만 지운다. **서버는 안 지운다.** 큐도 함께 비운다 |
| `부팅()` | 밖 | `if (ZG.서버 && ZG.서버.로그인됨) 시드를 심지 않는다` 한 줄. 안 그러면 새 기기에서 목데이터가 잠깐 깔렸다가 서버 것으로 덮인다 |

`?reset=1`은 **로컬만 지운다.** 서버는 그대로다 — 새로고침하면 서버에서 다시 내려온다. (지금까지처럼 「초기화」로 쓰려면 로그아웃 상태에서 해야 한다. 이 사실을 이사 화면에 한 줄로 적는다)

### 4-2. `01b-서버.js` 흐름

1. **게이트(동기)** — 토큰 없으면 즉시 로그인으로. 있으면 `ZG.서버.로그인됨 = true`
2. 화면은 기다리지 않고 뜬다(각 앱 파일의 `DOMContentLoaded → 시작()` 그대로)
3. **🔴 내려받기 전 관문 — §4-3.** 여기를 통과하지 못하면 **내려받기를 아예 안 한다**
4. **첫 내려받기** — 13개 표를 병렬로 `select *`(1,000건 넘는 표는 1,000씩 끊어서). 받은 즉시 `삭제됨=false`인 행의 `내용`만 모아 배열로 만들고 **`조용히(true)` 상태에서** 캐시·localStorage에 넣는다 → `설정쓰기({실데이터:true})` → `다시그리기()`
5. **Realtime 구독** — 채널 하나에 13개 표. INSERT/UPDATE/DELETE가 오면 그 표의 **그 줄만** 갈아끼우고 캐시·localStorage 갱신 → 다시그리기
6. **다시그리기 배분** — `ZG.앱`·`ZG.주문`·`ZG.업체앱`·`ZG.소싱앱` 중 이 페이지에 있는 것의 `다시그리기()`를 부른다. **앱 파일은 한 글자도 안 고친다**(네 개 다 이미 `다시그리기`를 내보내고 있다)
7. **에코 무시** — 방금 내가 보낸 `표+id`는 5초간 기억해 두고 되돌아오면 버린다. 입력 중 화면이 튀는 것을 막는다
8. **다시그리기 몰아치기 방지** — 200ms 안에 들어온 이벤트는 모아서 한 번만 그린다

### 4-3. 🔴 빈 서버가 찬 로컬을 덮지 못하게 — 관문 둘

표를 막 만든 직후의 서버는 **0건**이다. 그 상태에서 이사 데이터가 든 PC로 v3를 열면
「받은 즉시 캐시·localStorage에 넣는다」가 **주문 1,287건·품목 182개를 빈 배열로 덮고**, 그다음에 「☁ 서버로 올리기」를 눌러도 **올릴 게 없다.**
아래 **두 관문을 통과해야만** 내려받은 값이 로컬을 덮는다.

**관문 ① 「누가 한 번이라도 올렸는가」 — 서버상태 행**

`v3_공유설정`에 행 하나를 더 쓴다 — `id='서버상태'`, 내용 `{올림완료:true, 올린때, 올린기기, 건수:{품목:182, 주문:1287, …}}`.
**§7의 「☁ 서버로 올리기」가 다 끝난 뒤에만** 이 행을 쓴다.

- 부팅 때 **이 행 하나만 먼저 읽는다**(요청 1번, 수십 ms)
- **행이 없으면 → 내려받기를 통째로 건너뛴다.** 로컬은 손도 안 댄다. 화면 위에 노란 띠로 「아직 서버에 한 번도 올리지 않았습니다 — 이사 화면에서 **☁ 서버로 올리기**를 눌러 주세요」. 새 입력은 평소대로 로컬에 들어가고 큐에도 쌓인다(잃지 않는다)
- 행이 있으면 → 관문 ②로

왜 「받은 게 0건이면 안 덮는다」로 하지 않았나 — **0건이 정상인 표가 실제로 있다**(재고조정 2건·명세서 1건, 분류폴더는 0건일 수 있다). 0건을 근거로 삼으면 진짜 빈 표를 영원히 못 받는다. **「올린 적이 있다」는 사실 자체를 서버에 남기는 편이 틀릴 여지가 없다.**

**관문 ② 「서버가 로컬보다 적으면 멈춘다」 — 표 단위**

관문 ①을 지나도, 표마다 **서버 행 수(`삭제됨=true` 포함)** 와 **로컬 건수**를 견준다.

- 서버 ≥ 로컬 → 정상. 덮는다. (로컬에서 지운 줄은 서버에 `삭제됨` 표시로 남아 있으므로 서버가 적어질 이유가 없다)
- **서버 < 로컬 → 그 표는 안 덮는다.** 멈추고 「서버 주문 0건 / 이 기기 1,287건 — 덮지 않았습니다」를 띄운다. 사람이 **「서버 것으로 맞추기」를 직접 누를 때만** 덮는다
- 이 관문 하나로 「폰에서 실수로 올리기를 눌러 서버가 얇아진 경우」도 같이 막힌다

두 관문은 **첫 내려받기에만 걸린다.** Realtime으로 오는 줄 단위 갱신은 그대로 받는다.

## 5. 충돌 규칙 — 나중에 서버에 닿은 쪽이 이긴다(줄 단위)

| 경우 | 결과 |
|---|---|
| 폰과 PC가 **다른 줄**을 동시에 고침 | **둘 다 산다.** 지금 방식이면 하나가 통째로 사라진다. 이번 재개발의 첫째 이유 |
| 같은 줄을 동시에 고침 | 서버에 나중에 닿은 값이 남는다(`수정시각`이 트리거로 갱신). 진 쪽 화면도 Realtime으로 곧 이긴 값으로 바뀐다 — **조용히 어긋난 채 남지 않는다** |
| 같은 줄을 지우기 vs 고치기 | **지우기가 이긴다**(`삭제됨=true`가 마지막에 오면 그대로, 먼저 왔어도 고침은 삭제된 줄을 살리지 않는다) |
| 병합 | **안 한다.** 칸 단위 병합은 규칙이 복잡해지고 틀리면 조용히 값이 섞인다 |

## 6. 끊길 때 — 밭에서 인터넷이 없어도 일이 멈추지 않는다

- 쓰기는 **언제나 localStorage부터** 들어간다. 서버 전송은 그 뒤다 → 끊겨도 입력한 것은 남는다
- 못 보낸 것은 `zg.v3.보낼것`에 `{표, id, 값 또는 삭제, 시각}`으로 쌓인다. **같은 표+id는 마지막 것 하나로 합친다**(큐가 무한히 커지지 않게)
- 다시 연결되면(`online` 이벤트 · 30초 주기 · 창 다시 볼 때) 앞에서부터 100건씩 보낸다. 성공한 것만 큐에서 뺀다
- 화면 어딘가에 **못 보낸 건수**를 보여준다 — 위치·모양은 `dev-designer` 몫. 이번에는 `console`과 `ZG.서버.상태()`까지만 만들고 UI는 다음 단계
- 오래 끊겨 있다가 돌아오면 **먼저 받고(3) 나서 보낸다.** 내 옛 값이 남의 새 값을 덮지 않게 하기 위해서다

## 7. 이사 데이터 올리기 — 이미 브라우저에 있는 실데이터

`v3/이사.html`에 버튼 둘을 더한다(`js/99b-서버올리기.js`). 지금 이사 도구는 안 건드린다.

- **☁ 서버로 올리기** — 로컬 13개 표를 전부 읽어 `id` 기준 upsert. **500건씩 끊어** 보내고 진행률(`출고 1,272건 중 1,000…`)을 보여준다. 실패한 묶음만 다시 시도. 다 끝나면 건수 표를 찍는다
- 🔴 **13개 표가 전부 성공한 뒤에야 §4-3 관문 ①의 `서버상태` 행을 쓴다.** 도중에 하나라도 실패하면 안 쓴다 — 그래야 다음에 열어도 **반쯤 찬 서버가 로컬을 덮지 않는다**
- **⬇ 서버에서 받아오기** — 서버 것으로 로컬을 통째로 갈아끼운다(복구용·새 기기용). 「지금 브라우저 값이 지워집니다」 확인 한 번. **§4-3 관문 ②를 사람이 직접 넘는 길이 이 버튼이다**
- 🔴 **올리기는 사무실 PC에서 딱 한 번만 한다.** 폰에서 또 올리면 폰의 옛 값이 서버를 덮는다. 버튼 옆에 그 문구를 그대로 적는다

## 8. 우람님이 하실 일 — 순서대로

1. **Supabase 사이트에 들어가신다** → 왼쪽에서 **SQL Editor** → `New query`
2. 이 문서 §1의 회색 칸을 통째로 복사해 붙여 넣고 **RUN**. 「Success」가 나오면 표 13개가 생긴 것이다
3. 이어서 §2의 회색 칸을 붙여 넣고 **RUN**. 이건 **남이 못 보게 잠그는 것**이라 꼭 해야 한다
4. **두용씨 계정** — 왼쪽 **Authentication → Users → Add user**. 이메일·비밀번호를 넣으면 끝이다(나중에 하셔도 된다)
5. 개발팀이 배포한 뒤, **사무실 PC 크롬**으로 v3 이사 화면을 열고 로그인 → **「☁ 서버로 올리기」를 한 번** 누르신다. 몇 분 걸린다. 끝날 때까지 창을 닫지 않으신다
6. 그다음 **폰**으로 v3를 열고 같은 계정으로 로그인 → 주문·재고가 PC와 똑같이 보이면 성공이다
7. 확인 — **PC에서 입고를 하나 넣고 폰을 보신다.** 몇 초 안에 폰에도 보이면 다 된 것이다

⚠️ 5번은 **PC에서 딱 한 번만.** 폰에서 또 누르면 폰에 있던 옛 값이 서버를 덮어씁니다.
⚠️ 5번을 누르기 전에는 **서버가 비어 있는 게 정상**입니다. 그동안 v3를 열면 위에 노란 띠로 「아직 서버에 올리지 않았습니다」가 뜹니다 — **고장이 아닙니다.** 그 상태에서도 PC에 있던 주문·재고는 그대로 보이고, 입력하신 것도 안 없어집니다.
⚠️ 기존 `app.html`은 **아무것도 안 바뀝니다.** v3는 새 표를 따로 씁니다.
